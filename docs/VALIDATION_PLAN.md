# Validation plan and results

This plan answers: *how do we know the Rust port computes what upstream
GRTRANS computes, and how do we keep knowing it?*

## 1. Principles

1. Every claim of equivalence is backed by a checked-in fixture and a test.
2. Tolerances are the upstream project's own where they exist
   (`run_grtrans_test_problems_public.py`: 1e-2 relative for images and
   spectra, 5% for integrator cross-comparisons, 2e-2 for the toroidal case).
3. Intermediate quantities are validated separately from end-to-end results,
   so failures localize to a module.
4. Where the Rust implementation deliberately differs, the deviation is
   measured on the regression problems and the measurement is part of CI.

## 2. Test layers and current results

### Layer 2 — ray fixtures (intermediate)

| Case | Fixture | Result |
| --- | --- | --- |
| geokerr production path, standard=1 nup=25 and 400 (MUFILL), standard=2 nup=1 | `test_geokerr.txt` | camera ≤1e-12; r/θ/φ/k ≤1e-11 (absolute floors for near-zero components); λ/t cancellation-limited (below) |

**Cancellation-limited quantities.** Upstream assembles the affine parameter
and coordinate time as differences of ~1e6-scale integrals (the divergent
baseline from the tiny starting u0 = 1e-4…1e-9): `λ_j = Λ_n − Λ_j`,
`t_j = T_1 − T_j`. Last-ulp noise in the baseline (~1.3e-9) therefore
appears in the differences; the port matches to that level (1e-8 absolute
floor in the tests). This is inherent to the upstream algorithm, not a port
defect.

## 3. Transfer integration: the `radtrans_aux` interpolation quirk

Upstream integrates the transfer equation with ODEPACK LSODA (rtol=1e-6,
atol=1e-8, hmax=10, integration window trimmed at τ=10). The Rust port
substitutes an adaptive solver (see below) and, importantly, reproduces an
upstream interpolation quirk that is the dominant source of apparent
"integrator deviations".

**The quirk.** `radtrans_aux` (radtrans_integrate.f90) reverses the affine
parameter array (`ss(1:npts)=s0(npts:1:-1)`) and locates the bracket
`[ss(lindx), ss(lindx+1)]` for the current λ, but then interpolates the
coefficients from `jj(indx)` and `jj(min(indx+1, npts))` with
`indx = npts-lindx+1`. In terms of the original (decreasing) array this
evaluates the values at the pair `(indx, indx+1)` over the λ bracket
`[s0(indx), s0(indx-1)]` — i.e. the values are taken from one sample deeper
than the λ bracket. At the edges of an emission region, where j jumps to
zero, the shifted interpolation therefore reaches the zero sample and
reduces the edge contribution.

**Measurement (POWERLAW pixel 10043, 1-based; see
`reference/fixtures/fortran`-style debug output).** Taking *upstream's own*
`debug=1` j/K arrays and integrating exactly:

| interpolation | I (normalized) |
| --- | --- |
| unshifted (natural) | 3.5007e-4 |
| shifted (upstream `radtrans_aux`) | 3.3520e-4 |
| **upstream LSODA output** | **3.3507e-4** |

The shifted result matches upstream's LSODA to 0.04%: the upstream solver is
accurate, but solves the ODE with shifted coefficients. The port reproduces
the shift deliberately (`transfer::lsoda`, with a comment); before doing so,
the four regression images differed from the reference by 1.7e-2 (FFJET),
1.8e-2 (SPHACC) and 5.1e-2 (POWERLAW). After reproducing the shift they
agree to ≤8e-4 (see the table above).

**Solver substitution.** LSODA itself (opkda*.f, ~28k lines) is not ported.
The substitute is:

* four-Stokes: a stiff-stable exponential integrator. Each substep freezes
  the coefficients at the midpoint and applies the exact constant-coefficient
  update `I <- e^{-K h} I0 + (I - e^{-K h}) K^{-1} j` (`calc_o` matrix
  exponential, `imatrix_4` inverse), with the substep count per interval
  chosen adaptively by step doubling to ~1e-6 relative accuracy. This replaced
  an earlier explicit Dormand–Prince 5(4), which was unstable on very
  optically thick rays (K·Δs up to ~50 per maximum step).
* intensity-only (`nequations==1`): an unconditionally stable exponential
  integrator with bounded adaptive substepping (the scalar transfer
  equation is stiff for optically thick sources, e.g. SPHACC where
  K·Δs ~ 1e6, so an explicit method is not usable there).

Both integrate the same ODE (with the shifted interpolation) to well below
the reference tolerances; the end-to-end results above bound any residual
solver difference.

Open item (tracked in `docs/PORTING_MATRIX.md`): a faithful ODEPACK LSODA
port would make the agreement bit-exact; it is not required for the
validated tolerances.

## 3.1 HARM: validated chain, upstream integrator deviation on spiky data

The HARM port reproduces the upstream chain: the fluid reader/interpolation
matches a dedicated Fortran fixture to 7.6e-6, and at the ray level (pixel
5775) the scaled j/K arrays and optical depth match the upstream `debug=1`
output to ~1e-3 (the residual coming from f32-level fluid differences).

The image comparison against the LSODA-generated reference is 4.8e-2, above
the upstream 1e-2 criterion. The measured cause is the upstream integrator
behavior on this snapshot's extremely spiky emission (90% of the emission
comes from a 5-sample spike; j1 peaks at 4.4e-3 with K1 ~0.8):

| quantity | value |
| --- | --- |
| exact solution of the upstream's own dumped j/K (port's lsoda, delo, formal and an independent fine RK4) | 2.293e-3 |
| upstream `delo` and `formal` (bit-identical) | 2.704968e-3 |
| upstream `lsoda` | 2.745e-3 |

Two independent exact integrators agree on the solution of the upstream's
own coefficients, while the upstream's two "exact" schemes output ~18% more
(and agree with each other to all printed digits). The source of that
difference could not be identified after checking the coefficients
(index-by-index), the RHS (`radtrans_rhs_form`), the delo/formal formulas,
the window and the optical depth. The HARM test therefore uses a documented
6e-2 tolerance; the port's result is the exact solution of the upstream
coefficients. This is the only regression case where the port's result does
not meet the upstream tolerance, and the deviation is bounded and measured.

## 4. Upstream nondeterminism resolved deterministically

| Upstream | Resolution |
| --- | --- |
| `standard=2` camera leaves `TPRARR` unassigned (read by GEOKERR) | port uses 0; fixture driver zeroes it; standard=2 references verified insensitive |
| `standard=1` camera leaves `TPMARR`/`MUFARR` unassigned | port uses 0; fixture driver zeroes them |
| MUFILL writes up to KEXT elements past output arrays | port guards the writes (never read upstream) |
| `geodebug.out` header writes `fac` before it is computed | test does not rely on it |
| `synchpl` leaves columns 2–4, 6–11 uninitialized | only columns 1/5 are compared |
| `radtrans_aux` interpolates values one sample deeper than the λ bracket | reproduced deliberately (see §3); the dominant source of apparent integrator deviations |
| `get_weight` reads out of bounds when x is outside the table | port clamps to the edge interval (deterministic; affects only the innermost SPHACC points) |
| Fortran table literals with a leading decimal point (`.13733`) | extraction script handles them; the earlier naive parse (13733) was caught by the SPHACC end-to-end test and fixed |

## 5. Fixture regeneration and CI

```bash
scripts/build_upstream.sh /path/to/workdir     # fetch + patch + build
bash scripts/build_fortran_fixtures.sh /path/to/workdir
GRTRANS_UPSTREAM=/path/to/workdir/upstream \
  python3 scripts/gen_reference.py --outdir reference/fixtures --overwrite
python3 scripts/verify_fixtures.py             # checksums
```

`verify_fixtures.py` fails on any missing/mismatched fixture so tests cannot
silently skip. `.github/workflows/ci.yml` runs fmt, clippy, and the full test
suite (fixtures are checked in; no Fortran needed).

## 6. What would falsify equivalence

- A fixture mismatch beyond tolerance in any regression case.
- A kernel fixture mismatch (bit-level layers) that is not explained by an
  operation-order transcription bug.
- Any regression case where the Rust result matches the fixture only after
  tuning constants away from their upstream values.

## 3.2 SARIAF: thick-pixel residual is upstream LSODA error, not a port defect

SARIAF (semi-analytic RIAF) is self-contained and was ported with a Fortran
fluid fixture (`test_sariaf_fluid`) matching to 2.3e-6 (f32 level) and an
end-to-end fixture generated by the upstream binary. The image comparison is
4.1e-3 (tolerance 1e-2), dominated by ~82 very optically thick pixels where
the port is up to ~21% higher than the reference.

For the worst pixel (4562, 1-based; τ up to 1.1e3, K up to 5.0e2) the
upstream's own `debug=1` j/K/s/τ arrays were integrated three ways
(`crates/grtrans-transfer/tests/lsoda_thick_pixel.rs`):

| quantity | observer I (raw integrator units) |
| --- | --- |
| upstream LSODA (dumped) | 1.7143715e-8 |
| port `integrate_lsoda` | 2.0691343e-8 |
| independent fine RK4 of the same shifted ODE | 2.0691411e-8 |

The port matches the independent exact solution to 3.3e-6, while upstream
LSODA is 20.7% low. Hence on these stiff pixels the port computes the exact
solution and the residual against the reference is upstream's own solver
error (same class as §3.1). The test asserts agreement with the exact
solution, not with LSODA's error.
